제출 기획서는 산식·인수 기준(AC01~AC26)까지 갖춘 상세 설계서라, **계산 규칙은 제출 기획서를 그대로 따르고** 이 문서는 무엇을 1단계에 넣고 무엇을 미뤘는지를 적습니다.

## 1. 추진 배경과 현안

- 「복권 당첨을 꿈꾸는 모든 직장인들을 위해」 — 당첨됐다고 가정하고 집·여행·가족 선물·휴식 같은 계획을 **비용과 함께** 적어 보는 버킷리스트 시뮬레이터입니다.
- 핵심 경험은 **항목을 추가하거나 포기할 때 남은 예산과 「몇 달을 살 수 있나」가 즉시 바뀌는 것**입니다(제출 기획서 1장).
- 모든 잔고는 실제 계좌가 아닌 사용자가 입력한 **가상 계획의 계산 결과**입니다. 재무 조언이 아닙니다.

## 2. 목표

### 2.1 최종 목표 (제출 기획서)

| 구분 | 사용자가 확인할 핵심 결과 |
|---|---|
| 일시금 모드 (로또·스피또) | 세후 당첨금, 당첨 후 총잔고, 버킷 합계, 계획 후 잔고, 안전금고 제외 가용잔고 |
| 월 지급 모드 (연금복권) | 선택 월 수입과 지출, 해당 월 잔여금, 누적 잔액, 가용잔고, 지급 잔여기간 |
| 공통 | 버킷 편집과 실시간 재계산, 우선순위, 경고, 포기 비교, 퇴사 가능 기간, 결과 공유 |

사용 흐름: 복권과 등수 선택 → 당첨 건과 수량 추가 → 당첨금과 현재 잔고 설정 → 안전금고 설정 → 버킷 작성 → 예산 또는 월별 현금흐름 확인 → 비용과 일정 조정 → 결과 저장 및 공유.

### 2.2 1단계 목표 (이 리포)

제출 기획서 10장의 **P0(출시 필수·연금 핵심·재미와 보존)** 를 간결하게 줄여, **계산 엔진이 5장 계산 예시와 세금 구간 경계를 정확히 재현**하는 것을 최우선으로 합니다(제출 기획서 10장 「1단계는 계산 엔진과 상품·세율 설정을 구현하고 5장 예시 및 경계 테스트를 통과한다」).

- 설치 없이 도는 정적 웹, 계정 없이 이 브라우저에 저장(제출 기획서 8장 「MVP는 계정 없이 브라우저 로컬 저장」).
- 상품 초기값은 **제출 기획서에 적힌 값만** 쓰고 「기획서 기준 값 · 확인일 2026-09-29」로 표시합니다. 모두 고쳐 쓸 수 있습니다.
- 로또 1~3등 평균값은 **수집 자료 파일(`data/lotto.json`)이 있으면 자동으로, 없으면 직접 입력**합니다(2026-09-30 수강생 답). 자동 수집 연결은 공식 공개 경로가 확인될 때까지 보류합니다(11.2).

## 4. 해결 방안 개요

```mermaid
flowchart LR
  W[당첨 내역<br/>복권·등수·수량<br/>1건당 세전/세후] --> T[과세 단위별 세후<br/>q × net&#40;G&#41;]
  T --> M{월 지급이 있거나<br/>수령 월이 다른가}
  M -- 아니오 --> LS[일시금 대시보드<br/>C₀+N−버킷 = B, A = B−S]
  M -- 예 --> MS[월별 현금흐름<br/>Rₜ = Iₜ−Fₜ−Qₜ<br/>Bₜ = Bₜ₋₁+Rₜ]
  B[버킷·고정지출·안전금고] --> LS & MS
  LS & MS --> O[경고 4단계 · 포기 비교<br/>퇴사 가능 기간 · 공유 이미지]
```

| 단계 | 내용 |
|---|---|
| 입력 정규화·검증 | 원 단위 정수, `YYYY-MM`, 수량 1~100, 금액 0~1조원, 오류 행은 계산 제외(제출 기획서 7·8장) |
| 과세 | 과세 단위(게임·낱장)마다 세후를 먼저 구하고 수량을 곱함 — `net(q×G)` 가 아니라 `q×net(G)` (2B) |
| 월별 확장 | 일시금은 수령 월 한 번, 연금은 첫 지급 월부터 K개월. 시작 월 전 지급분은 현재 잔고와 중복하지 않음 |
| 누적 계산 | 시작 월부터 600개월, 음수를 0으로 보정하지 않음(4장) |
| 지표 | 경고(현금 부족 → 안전금고 침범 → 월 적자 → 낮은 여유), 첫 부족 월, 연금 종료 월, 퇴사 가능 기간 |

**1단계에서 줄인 규칙** (간결하게 가기 위한 해석 — 10장에서 확인 요청)

- 일시금 모드와 월별 모드는 제출 기획서대로 **자동 판정**합니다(월 지급이 있거나 수령 월이 다르면 월별). 일시금만 있어도 「월별 현금흐름으로 보기」를 켤 수 있습니다. 모드 전환 때 「별도 시나리오 생성」 대신, 일시금 화면에서는 반복 버킷을 합계에서 빼고 그렇다고 알려 줍니다(버킷은 그대로 보존).
- 버킷 폼의 지출 월은 시나리오 시작 월로 미리 채워 두어, 월별 모드로 바뀌어도 지출 월이 비지 않게 했습니다. 비어 있으면 「입력 확인 필요」로 계산에서 뺍니다.
- 기본 조회 기간은 「전체 종료 월 이후 12개월」에 **가장 늦은 예정 지출 월**도 포함해 넓혔습니다(예약 지출이 조회 밖으로 밀리지 않게). 계산은 늘 600개월입니다.

### 11.1 구현 규칙

- **추가 예상 수입** — 「4. 고정지출과 기타 수입」의 구분에서 고릅니다. 월 금액(세후)·시작 월·종료 월(필수), 이름은 비우면 「추가 예상 수입」. 그 기간 월별 예산의 수입 Iₜ 에 들어가고, 하나라도 있으면 월별 현금흐름으로 봅니다(기간 예산에 연동해야 하므로).
- **안전금고 한도(확정)** — 일시금: 당첨 후 잔고. 월별: `현재 잔고 + 시작 월 당첨 수령액 + Σ(추가 예상 수입 월 금액 × 시작 월 이후 기간 개월 수)`. 2단 「잔고와 안전금고」에 식을 풀어서 보여 주고, 추가 예상 수입을 지워 한도가 금고보다 작아지면 알려 줍니다.
  - 미래 수입까지 한도에 넣으므로 그 수입이 들어오기 전 달에는 「안전금고 침범」 경고가 날 수 있습니다. 계산은 기존 규칙(가용 = 잔고 − 금고) 그대로입니다.
- **그래프 기간** — 보기 시작·끝 월(계산 범위 600개월 안으로 자동 맞춤, 거꾸로 넣으면 바로잡음), 1년·3년·10년·기본 기간 단추. 고른 기간은 시나리오에 저장되고 표도 같은 기간을 보입니다.
- **공유 링크** — 시나리오를 JSON → base64url 로 바꿔 주소 `#share=` 뒤에 붙입니다. `#` 뒤는 서버로 전송되지 않아 GitHub Pages 에도 남지 않습니다. 「현재 잔고」를 고르지 않으면 잔고·안전금고를 0원으로, 「버킷 메모」를 고르지 않으면 메모를 비우고, 회차·복권 별칭·게임 위치는 늘 뺍니다. 받는 쪽은 알림 상자에서 「내 목록에 추가」를 눌러야 복사되고, 보낸 사람의 계획은 바뀌지 않습니다. 서버가 없으니 **보낸 링크를 철회할 수는 없습니다**(철회는 계정·서버가 필요한 2단계).

### 11.2 로또 평균 자동 수집을 보류한 이유

- 정적 사이트(브라우저)에서 동행복권 화면을 직접 읽는 것은 CORS 로 막히고, 화면을 긁는 방식은 운영사 약관 존중 원칙에 맞지 않습니다.
- 그래서 **리포 안 GitHub Actions 예약 작업이 공식 공개 JSON 주소를 하루 한 번 읽어 `data/lotto.json`(최근 52회차 1~3등 1게임당 금액)을 커밋**하는 방식을 검토했고, 조건은 「공개 문서화되어 있고 이용이 허락된 주소」였습니다.
- 2026-09-30 확인 결과 **조건을 만족하는 주소를 찾지 못했습니다.**
  - 동행복권은 당첨 결과 API 를 공식 문서로 제공하지 않습니다(개발자 안내·오픈 API 페이지 없음).
  - 블로그 등에서 널리 쓰이던 비공식 주소 `common.do?method=getLottoNumber&drwNo=…` 는 2026-09-30 현재 **홈페이지로 넘겨집니다(HTTP 302)** — 사이트 개편 뒤 막힌 것으로 보입니다. 이 주소도 1등 금액만 주고 2·3등은 없었습니다.
  - 공공데이터포털에 있는 온라인복권 자료는 1등 판매점 현황 파일이라 1~3등 회차별 당첨금이 없습니다.
- 그래서 **긁어오지 않고**, 자료 형식(`lotto-draws@1`)과 읽기·평균(최근 52회차, 당첨자 0명 회차 제외, `round(ΣP/N)`)·직접 입력만 만들었습니다. 지금 `data/lotto.json` 은 비어 있어 앱은 직접 입력으로 동작합니다.
- 공식 공개 경로가 생기거나 운영자가 결과 화면을 보고 `data/lotto.json` 에 회차를 적어 넣으면(관리자 등록), 앱은 코드 수정 없이 평균을 자동으로 채웁니다. 예약 작업은 그때 붙입니다.
