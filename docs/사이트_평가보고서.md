# 행복회로 버킷리스트 사이트 평가보고서

- 평가대상: `https://aebonlee.github.io/data09-23/`
- 평가기준: 업로드된 저장소의 기존 구현과 2026-09-29 디자인 개선본
- 평가 관점: 20년차 웹개발 PM / 서비스 UX / 외부 공개 적합성

## 1. 총평

이 프로젝트의 강점은 디자인보다 기능 설계에 있다. 단순한 “복권 당첨금 계산기” 수준이 아니라 여러 복권/등수, 세전·세후, 연금형 수입, 버킷리스트, 안전금고, 고정지출, 월별 현금흐름, 퇴사 가능 기간, JSON 백업과 이미지 공유까지 연결되어 있어 기능 범위가 넓다. 특히 계산 로직 테스트가 별도 분리되어 있어 수강생 과제 수준을 넘어 유지보수 가능한 구조를 갖추고 있다.

기존 UI의 약점은 기능이 많은 만큼 첫 인상이 복잡하다는 점이었다. 서비스 소개 없이 곧바로 입력 폼이 노출되고 브랜드 시그니처가 없어 “왜 쓰는 사이트인지”보다 “무엇을 입력해야 하는지”가 먼저 보였다. 디자인 개선본에서는 이를 브랜드·히어로·3단계 가이드·단계 라벨·결과 대시보드 강조로 보완했다.

## 3. 잘된 점

### 3.1 계산 엔진과 UI가 분리되어 있다

`logic.js`에 계산 규칙이 집중되어 있고 테스트가 별도로 존재한다. 디자인 개편을 하면서 계산 결과를 건드리지 않고 화면만 바꿀 수 있었던 이유다.

### 3.2 사용자 데이터가 로컬 중심이라 1단계 서비스에 적절하다

계정 없이 localStorage와 JSON 백업을 사용하는 구조는 교육용/프로토타입 서비스에 적합하다. 서버 개인정보 보관 부담이 적다.

### 3.3 월별 시뮬레이션이 차별점이다

일시금만 빼는 계산보다 연금형 수입, 반복 지출, 특정 월 지출, 퇴사 시 급여 중단까지 다루기 때문에 서비스 컨셉을 설명할 수 있는 충분한 깊이가 있다.

### 3.4 접근성 기본기가 좋다

`label`, `aria-live`, skip link, focus 스타일, 텍스트 경고가 이미 포함되어 있었다. 기능 과제에서 흔히 빠지는 부분이지만 이 프로젝트에는 기본 구조가 존재한다.

## 4. 개선 전 주요 문제

### 4.1 메인 페이지가 없었다

`index.html`은 사실상 입력 앱 그 자체였고 소개/브랜드/가치 제안 영역이 없었다. 외부 방문자는 복권 관련 입력 항목부터 마주하게 된다.

### 4.2 브랜드 기억점이 약했다

보라색 컬러와 텍스트 이름은 있었지만 로고, 컬러 체계, 브랜드 영문 보조명, 시각적 상징이 없어 공유 후 기억에 남기 어려웠다.

### 4.3 결과보다 입력이 더 강하게 보였다

사용자는 “얼마 남는가”를 보기 위해 입력하는데 화면상에서는 입력 섹션과 결과 섹션의 무게가 비슷했다.

### 4.4 공개 검색 설정과 맞지 않았다

`robots=noindex`는 개인 과제 단계에서는 타당하지만 외부 서비스 전환 목표와는 맞지 않는다.

## 5. 개선 후 디자인 평가

### 브랜드

딥 퍼플과 민트 조합은 “상상/꿈”과 “계획/성장”을 동시에 표현한다. 금색·빨강을 전면에 쓰는 전형적인 복권 디자인을 피했기 때문에 사행성 홍보 이미지보다 계획 도구에 가깝게 보인다.

### 히어로

“당첨되는 상상”을 시작점으로 쓰되 최종 행동을 “내 꿈의 가격을 계산”하는 것으로 재정의했다. 이는 사이트의 재미 요소를 유지하면서도 도구의 목적을 설명한다.

### 카드/입력 UI

기존 10px 라운드/선 중심 UI에서 16px 카드와 얕은 그림자를 적용해 서비스 완성도를 높였다. 과도한 그림자나 그라데이션은 히어로와 CTA에만 제한했다.

### 결과 대시보드

`DASHBOARD` 라벨과 별도 깊이감을 적용하여 사용자의 시선이 계산 결과로 이동하도록 했다.

## 6. 남은 리스크

1. Open Graph 대표 이미지는 아직 없다. SNS 공유 품질을 위해 1200×630 이미지가 필요하다.
2. 첫 방문 사용자가 빈 화면에서 어떤 숫자를 넣어야 할지 어려울 수 있다. 현재 예시 버튼이 있지만 히어로 CTA에서 “예시로 체험”을 직접 제공하면 더 좋다.
3. 2단계에서 서버/계정이 들어가면 개인정보 처리, 데이터 삭제, 장애 대응이 필요하다.
4. 복권 세금/당첨금 기준값이 외부 데이터로 자동화되면 기준일·출처·업데이트 실패 상태를 UI에 명시해야 한다.
5. 자동화된 브라우저 기반 UI 테스트는 현재 저장소에 없다. Playwright/Cypress 도입을 권장한다.
